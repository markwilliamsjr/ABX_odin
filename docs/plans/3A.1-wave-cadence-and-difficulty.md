# Roadmap 3A.1 — Wave cadence and difficulty ramp

Status: active
Roadmap: ROADMAP.org 3A.1
Decisions: DECISIONS.md "Wave pressure", "Wave handoff", "Enemy counts",
"Early-level determinism", "Determinism"
Session: SESSION.md
Docs updated: 2026-11-24

Steps only, no code.

## Scope

Make wave-to-wave pressure non-decreasing and start the next wave before the
current one has fully resolved. It does not add formation variety, multiple
regions, or position-based species placement. Player-visible behavior changes:
clusters no longer shrink at level 2 and the idle gap between waves goes away.

## Decisions already settled

- Difficulty is measured by **peak simultaneous enemies**, and each level's peak
  must be non-decreasing. (DECISIONS "Wave pressure")
- The next wave overlaps the current wave's resolve and flee phase. A wave still
  ends only when all of its own members resolve; that is no longer a global gate
  for the next wave's spawn. (DECISIONS "Wave handoff"; ARCHITECTURE "Ending a
  wave")
- `3 + level*2` is a level-wide budget split across waves with a floor of three;
  the floor wins. (DECISIONS "Enemy counts")
- Wave count is a seeded structural draw with inclusive ranges; level 1 is always
  one wave of five. (DECISIONS "Level composition", "Early-level determinism")
- Decisions are tick-driven, never wall-clock. Phase 2 must have landed before
  this step tunes cadence. (DECISIONS "Determinism")
- Every generated value derives from `derive_seed`; a wave seed is a pure function
  of run seed, level, and wave index, with no run history. (DECISIONS "Seeding")

## Steps

### 1. Clamp the drawn wave count — `src/level.odin`, `level_init`

- Plugs into the share computation immediately after `wave_count_picker` and
  before each `wave_init` call.
- Constrain the drawn count so the largest share a level can field is never below
  the previous level's peak. Use a budget-derived bound, not carried run state.
- Keep the seeded draw, the floor, and the block ranges intact; only the upper
  bound is constrained.

Check: level 1 is still one wave of five across seeds; no level-2 seed yields a
cluster smaller than five; shares never fall across levels 1–12 for a fixed seed.

### 2. Separate first-spawn delay from spawn interval — `src/level.odin`,
`wave_init` / `wave_update`

- Plugs into `spawn_timer` and `spawn_delay` in the spawning branch of
  `wave_update`.
- Keep `spawn_delay` as the between-spawn interval. Give each wave its own start
  delay; set it to zero (or one tick) for a wave that follows another in the same
  level so the handoff does not pay the full interval twice.
- Do not change how a shortfall or a failed spawn is handled.

Check: the first spawn of wave N+1 lands on the handoff frame or the next tick,
while within-wave spacing stays at `spawn_delay`.

### 3. Allow overlapping waves — `src/game.odin`, `world_update`

- Plugs into the `if level.wave_index < level.wave_count` block in the `.Playing`
  branch.
- Replace the single `wave[wave_index]` target with a bounded active window of
  wave indices. Each wave keeps its own spawn timer, ownership, threshold test,
  flee phase, and counters.
- `wave_resolution_update` still advances per wave and sets `level_end` only when
  the last wave resolves. The roster tick still fires once per completion.
- Ownership is already wave-index-based, so multiple active waves need no new
  identity field. Do not introduce a composite `(level, wave)` key.

Check: two waves can have active members in the same frame; no frame has zero
owned bacteria while the level is still playing; kill counts still land on the
owner wave.

### 4. Verify

- Record the new share table and spawn timestamps; run the same-seed replay
  comparison against the baseline.

## Open choices

**1. How to bound the wave count.**
- Cap the count by `budget / MIN_SHARE`: uses no run history and preserves the
  seeded draw — recommended.
- Clamp against the previous level's peak: exact, but introduces carried state
  that wave seeds currently avoid.
Recommendation: cap by `budget / MIN_SHARE`, with `MIN_SHARE` a tuning constant.

**2. How many waves may be active at once.**
- One wave ahead only: bounded state, easy to reason about, enough to remove the
  gap — recommended.
- All remaining waves active: maximum overlap, but every wave's timers run and
  the screen can saturate.
Recommendation: one wave ahead; the seam must not prevent widening later.

**3. First spawn of an overlapping wave.**
- One tick after handoff: keeps the update order simple and observable —
  recommended.
- Same frame as handoff: marginally tighter, but mixes spawn with resolution in
  one frame.
Recommendation: one tick.

## Deliberately not doing

- V and semicircle layouts, multiple regions per wave, and per-position species
  placement. Steps 3A.2–3A.4 own those.
- Entry path variety and simultaneous-diver changes — step 3A.5.
- Flee animation and per-species behavior — Phase 6. The seam left here is that
  the next wave's spawning must not depend on the previous wave's flee phase
  duration; adding duration must not restore the gap.
- Boss tuning and adaptive composition — Phases 8 and 9.
